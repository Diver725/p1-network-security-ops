## 任务卡 C（已完成 2026-09-13）：WAF 拦截 SQL 注入并处置

**目标**：让一个 Web 站点处于 WAF 保护之下，正常访问能通、SQL 注入被拦截，并完成"拉黑攻击源 → 验证 → 恢复"的处置闭环。

**前置环境**：p1-pfsense、p1-web（.102）、p1-waf（.103）；操作机 Windows。

**验收标准**
- [x] 浏览器访问 WAF 地址能看到 Web 页面（正常放行）
- [x] 发起 SQL 注入请求，返回 403 且出现 WAF 拦截页面
- [x] WAF 控制台能看到该攻击事件（类型、来源 IP、时间）
- [x] 把攻击源 IP 加入黑名单后，正常访问也被拒绝（403）
- [x] 移除黑名单后，访问恢复正常（200）

**卡点记录（2026-09-13）**
- 不熟悉日志文件路径结构（/var/log/nginx 各段含义）→ 已理解，并练习用 ls 逐层探索
- URL 查询参数结构与百分号编码不熟 → 已理解参数与值的结构，知道编码可交给工具处理
- 浏览器缓存导致「黑名单没生效」的误判 → 用 Ctrl+F5 / curl 看状态码验证解决
- 概念卡点：SQL 注入中单引号的作用（逃出字符串 + 补齐引号）→ 已理解
- 求助方式：以概念提问为主（不是让 Codex 代做命令）

**耗时**：约 40 分钟

## 任务卡 A（已完成 2026-09-13）：fail2ban 封禁验证

**目标**：从另一台机器制造 SSH 登录失败，验证目标机 fail2ban 自动封禁来源 IP，并完成解封。

**前置环境**：p1-pfsense、p1-lan-client（.100）、p1-web（.102，作为攻击源）。

**验收标准**
- [x] 在 p1-web 上对 .100 发起多次错误密码尝试
- [x] 在 .100 上看到封禁状态里出现 p1-web 的 IP，且失败次数统计正确
- [x] 解封后恢复正常
- [x] 能解释：为什么在本机（127.0.0.1）测试不会触发封禁

**卡点记录（2026-09-13）**
- 忘了 ignoreself 规则：本机 127.0.0.1 来源的失败会被忽略（防止自锁），测试必须从另一台机器发起
- 第一次查到 5 次失败但未封禁：fail2ban 处理日志有秒级延迟；且封禁后 Currently failed 会清零，导致数字看起来「对不上」
- 理解了 server / client 的区别：server 后台干活，client 是发指令的入口工具
- 学会：`fail2ban-client status` 列出所有 jail；`fail2ban-client status <jail>` 看详情；`fail2ban-client unban <IP>` 解封
- 忘了 for 循环与 sshpass 的用法 → 已重新理解（for 循环结构 + sshpass 喂密码）

**耗时**：约 25 分钟

## 任务卡 B（已完成 2026-09-14）：给一台机器接入 Wazuh Agent

**目标**：把一台 Ubuntu 机器接入 Wazuh，做到"Endpoints 显示 Active，且能搜到它的日志"。

**前置环境**：p1-pfsense、p1-wazuh（.101）、任选一台目标机（如 p1-web .102）。

**验收标准**
- [x] 目标机安装并启动 Wazuh Agent，配置指向 .101
- [x] Wazuh 控制台 Endpoints 显示该机 Active（p1-waf，agent id 003）
- [x] Discover 中能按 `agent.name` 搜到该机日志
- [x] 说明：Agent IP 显示 any 有无影响（不影响采集：Agent 主动连 Manager）

**提示方向**：安装命令从哪来（控制台向导）？服务如何设开机自启？日志索引与时间范围怎么选？

**卡点记录（2026-09-14）**
- 忘了 Agent 该选 DEB 还是 RPM、amd64 还是 aarch64 → 已理解判断方法：看发行版（Ubuntu=DEB）与架构（uname -m 输出 x86_64 对应 amd64）
- 把 Server address 填成了 .103（误把被监控机器当成服务器）→ 已纠正：Server address = Wazuh 服务器(.101)；Agent name = 被监控机器(p1-waf)
- Agent IP 显示 any 的含义：不影响采集与告警（Agent 主动连接 Manager 的 1514 端口）
- 学会用 Endpoints 看 Agent 状态、在 Discover 按 agent.name 搜索日志
- 意外收获：发现 Wazuh 自带 SCA 基线评估功能，p1-waf 的 CIS 基线得分仅 50（118 项未通过），可作为后续加固输入

**耗时**：约 25 分钟

**目标**：检查一台机器的 SSH 加固是否真的生效（不是看配置文件，而是看实际生效值）。

**前置环境**：p1-pfsense、p1-lan-client（.100）。

**验收标准**
- [x] 显示 SSH 实际生效的加固项（禁 root、尝试次数、允许用户、空闲超时）
- [x] 说明每项防的是什么风险
- [x] 说明改配置的标准流程（备份 → 改 → 语法检查 → 重启 → 另开窗口验证）

**卡点记录（2026-09-13）**
- 忘了当初怎么配置加固项（怀疑是参数名=值）→ 已澄清：sshd_config 用「参数名 + 空格 + 值」；通过 drop-in 文件 /etc/ssh/sshd_config.d/99-hardening.conf 添加，主配置不动
- 忘了语法检查（sshd -t）的作用 → 已理解：只校验语法不重启服务，防止配置写错导致 SSH 起不来、把自己锁在门外
- 能独立复述 5 步流程：备份 → 追加加固配置 → 语法检查 → 重启服务 → 另开窗口验证
- 学会用 man sshd 查选项含义；学会 grep 的两种输入来源（文件 / 管道）
- 理解了 ssh 与 sshd 的区别（客户端 vs 服务端守护进程）

**耗时**：约 20 分钟
